# Jamf School

Use this path when you manage an iOS/iPadOS fleet through Jamf School and want workbook
reporting from `jamf-cli school` data. A connected School profile and a collect are what fill
the workbook; a Jamf School device CSV export on its own does not add sheets yet.

It produces a standalone Jamf School workbook with sheets for device inventory, OS
versions, device status, stale devices, overview, device groups, users, classes, apps,
profiles, and locations, all generated by the native Swift engine.

## Prerequisites

Install `jamf-cli` (v1.29.0 or later; see [Installation](https://github.com/tonyyo11/jamf-reports-community/wiki/01-Installation)).
Connect a Jamf School profile from the app by choosing the Jamf School product during
onboarding. Jamf School gets its own workspace and is not added to a Jamf Pro workspace.
The app runs `jamf-cli school setup` for you and wires `school_cli.enabled`/`profile` into
`config.yaml`. (In a `config.yaml` with a `profiles:` block, the School profile is the
`profiles.jamf_school` slot instead, which onboarding writes there.)

The relevant `config.yaml` section (the app manages it):

```yaml
school_cli:
  enabled: false          # true when using live jamf-cli school commands
  profile: "school"       # the workspace's own profile; blank means the same
```

School snapshots are stored under `jamf_cli.data_dir` with the rest of the workspace's data.

## Setting up a School-only workspace

On the app's first-launch **Welcome chooser**, click **Connect Jamf School**. This runs a
dedicated Jamf School onboarding path — Welcome, Install CLI, Workspace, Workspace config,
**Connect School**, First report — that skips the Jamf Pro Authenticate, Validate, and
Add-products steps entirely. The Connect School step registers a `jamf-cli school` profile
(School URL + Network ID + API key, passed over stdin and cleared) and wires
`school_cli.enabled`/`profile` into the workspace config, so the first report and every
later collect route to the Jamf School engine. `jamf-cli` must still be installed to pass
the Install CLI step (a free Homebrew binary, no server access needed), but you never enter
Jamf Pro credentials.

### Platform API for Jamf School (experimental)

If your Jamf School tenant also has a Jamf Account integration for the Platform API (used for
blueprints), turn on **Do you also have Platform API configured for Jamf School?** in the
Connect School step and fill in the region, tenant ID, client ID and client secret. These are
not a separate jamf-cli profile: jamf-cli's `school setup` saves them on the School profile
itself. After saving, the app lists the tenant's blueprints once to check the fields and shows
the result: a tenant ID the gateway does not accept, or an integration without
`blueprints:read`, is named, and the School API key keeps working either way.

To add or change them later, open **Data Sources** on the School workspace and use **Add…** or
**Update…** on the Platform API card. jamf-cli rebuilds the whole profile when it saves, so the
sheet asks for the Network ID and API key as well. **Update credentials** on the same screen
opens with the Platform API switch on when the profile already has the fields; saving with it
off removes that access, and the sheet says so. Please report how this works on your tenant on
GitHub.

If you run Jamf School, please
[open an issue or pull request](https://github.com/tonyyo11/jamf-reports-community/issues)
with feedback.

Earlier builds could connect Jamf School to a Jamf Pro workspace, which wrote a
`school_cli.profile` naming a second jamf-cli profile. That workspace now collects Jamf Pro
again and the School profile is not used; Config Doctor warns about it. Set
`school_cli.enabled: false` there and set Jamf School up as its own workspace.

A Jamf School workspace shows only the screens that apply to it: Overview, Devices, Trends,
Generated, Automation, Run History, Config, Data Sources and Settings, plus Jamf
Protect and Backups while Protect is connected (a School workspace backs up Protect alone). The Jamf Pro screens, Fleet Overview included, leave the
sidebar while it is the active workspace (your own hidden-tab choices are kept for the
others), and Settings › Sidebar Visibility lists only the screens the workspace has. The rest
of the dashboards in [Dashboards](https://github.com/tonyyo11/jamf-reports-community/wiki/03-App-Dashboards)
are Jamf Pro surfaces. On a School workspace:

- **Overview** shows School's own data: device counts by platform, managed, supervised and
  stale devices, and each count Jamf School reports (users, classes, apps and the rest).
- **Devices** lists the devices Jamf School manages (name, serial, model, OS, managed,
  supervised, last check-in) with counts by platform, Managed, Unmanaged and Stale filters
  and a search. Devices waiting in Automated Device Enrollment are listed below them.
- **Config** keeps Thresholds (only the stale threshold), Output and the From file tab.
- Generate opens on the School template and offers the workbook only. Data Sources lists the
  `jamf-cli school` commands a collect runs. The health banner and launch checks no longer
  judge the workspace by Jamf Pro reports.
- **Automation**'s Data Freshness card describes School's daily collect; the weekly deep scan
  applies to Jamf Pro workspaces only.

### Blueprints (experimental)

When the School profile has the Platform API fields (see above), a collect also reads the
tenant's blueprints and the workbook gets a **Blueprints** tab: name, state, last deployed,
created and updated. Without those fields Data Sources shows the source as skipped and says
how to add them.

### Device health

The School **Overview** has a **Device health** card, and the School workbook has a **Device
Health** tab at the end. Both come from data a School collect already saves:

- devices assigned in Automated Device Enrollment that are not enrolled, with a breakdown by
  the status Jamf School gives and by enrollment profile
- users with no device
- device groups with no members, smart and normal groups counted apart
- classes with no devices, no students or no teacher

Every figure is a plain count out of its total, with no colour and no warning: in most
districts many users have no device and many groups are empty, so the app does not call
either a problem. A figure whose data was not collected is left out, and one whose data could
not be read says so.

**Per-device scan.** The device list does not carry battery, enrollment type or storage, so a
collect reads them one device at a time and adds them to the card and the workbook:

- The Device health card gains enrollment type and storage breakdowns, how many devices had a
  battery between 1 and 20% when scanned, and how many reported a battery of 0, which is shown
  apart from the 1 to 20% count. It also shows when the
  last scan ran, or that the last attempt failed.
- The workbook's **Device Inventory** tab gains three columns at the end: Enrollment,
  Storage (GB) and Battery (%) when scanned. The Device Health tab gets the same counts.

Battery is the reading taken when the device was scanned, not a live value. The scan runs at
most once every 7 days, on a run that includes the scan tier, and a manual collect does not
force it sooner. A scan that fails never fails the School collect: the run still reads as
successful and the card says the last attempt failed. To turn the scan off, use its switch on
**Data Sources**, which writes `school-device-detail` to `jamf_cli.collect_skip`:

```yaml
jamf_cli:
  collect_skip: [school-device-detail]
```

Jamf Pro workspaces skip the Mac or mobile sources when the fleet has none of those devices;
a Jamf School workspace does not, because its one device list covers every platform.

### Jamf Protect with Jamf School (experimental)

Jamf Protect can be connected to a School workspace from Data Sources or the **Add** sheet.
Protect is then collected after every School collect, gets its own **Jamf Protect** screen
and adds its tabs to the School workbook. Its **Jamf School match** card matches Protect
computers to Jamf School Macs by hardware UUID, then serial number, never by name. A School
workspace backs up Protect alone (2.12): the **Backups** screen, `jamf-reports backup` and
scheduled backups run `jamf-cli protect backup` and no Jamf Pro backup, and Diff is not offered
for these backups. Please report how this works on your tenant on GitHub.

## CSV export format

Jamf School CSV exports are not read. The School workbook is built from the data
`jamf-cli school` collects.

## Using the app

1. Connect a Jamf School profile (onboarding, or **Data Sources** later).
2. Collect, then generate the Jamf School workbook from the app. Its sheets come from the
   collected School data.
3. Each collect that reads the devices saves a daily summary, so **Trends** builds history:
   Macs and mobile devices are counted apart (managed, supervised, stale by last check-in, and
   on the current OS against the SOFA feed each collect reads; `collect_skip: sofa` leaves it out), and
   the first run also fills earlier days from the device snapshots already saved. The workbook's
   **Trends** tab lists the same figures, one row per day. Jamf School does not report passcode,
   encryption or jailbreak state, so those mobile figures are not shown for a School workspace.

## What jamf-cli school commands are used

A School collect calls `school overview`, `school devices list`, `school device-groups
list`, `school users list`, `school classes list`, `school apps list`, `school profiles
list`, `school locations list`, `school ibeacons list`, and `school dep-devices list`.
