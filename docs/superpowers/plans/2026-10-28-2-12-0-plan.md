## 4. Subagent-driven development mechanics

The loop follows [docs/superpowers/agent-loop.md](../agent-loop.md): a subagent only where work runs
in parallel in a fresh context, is independent verification, or reads far more than the loop needs;
everything deterministic is a skill. The controller verifies conclusions itself (reads the diff,
runs the suite) and decides, briefs, rules and keeps the ledger.

**Roles that stay subagents**

- Implementer (Sonnet; Opus for 2.1–2.3, 3.4, 5.2, hard debugging), one per task, in its own
  worktree off `dev/2-12-0`. Brief = task row + spec section + the review checklist + "fixtures
  captured, never written from docs" + the honesty-chain and entry-point lists for anything that
  adds a source or product. It returns status, commits and counts; its report file is the
  hand-off.
- `reviewer` (Sonnet) on every task; `security-reviewer` (Opus) for 1.4, 1.6, 1.15, 2.x, 5.2 and
  anything that reads or writes workspace files, adds a product gate or sends data out. Each cites
  checklist numbers. A finding of a known class sweeps the siblings in the same PR.
- Research and comparison agents (web pages, another repository, a long log).

**Folded into the controller**

- A scoped re-review of a fix round is the controller reading the diff and the report when the
  fix diff is under about 150 changed source lines (`git diff --shortstat FIX_BASE..HEAD -- app/Sources`)
  and adds no new seam, file write path or product gate. Otherwise a re-review is dispatched. The
  ledger line says "controller read the diff"; a defect found while reading turns it into a
  dispatch.
- Brief writing, fix-round composition, rulings, the ledger.

**Skills (`.claude/skills/`), used instead of retyped shell**

| Step | Skill |
|---|---|
| Review file for BASE..HEAD | `review-package` |
| Sibling sites of a seam, plus the twelve class greps, with the PR-body block | `class-sweep` |
| CHANGELOG merge or rebase conflict | `changelog-union` |
| Merge approved branches into a wave bundle (never pushes) | `bundle-wave` |
| Adopt branches into a `gh stack` (person-started, never submits) | `stack-adopt` |
| Full suite from a local-disk worktree at a tip | `tip-test` |
| Score the wave's ledger against the baseline | `loop-eval` |

**Gate before a PR:** `swift build --build-tests` on the host, filtered `swift test`, `tip-test` on
the branch or stack tip, and a CI-parity VM run (the maintainer's `vm-test` skill) for anything
touching isolation or AppKit. CHANGELOG line per PR, release-notes voice; epic #305 item ticked with
the SHA on merge.

**Eval.** At the end of each wave run `loop-eval <ledger> --wave <name> --baseline
docs/superpowers/agent-loop-eval/2026-10-28-waves-0-6.json`. It reports rounds to approval,
reviews and verdicts with MUST-FIX / SHOULD-FIX / CONSIDER tags, re-review seats, controller reads
and the suite figure. A change to the loop (a folded seat, a new skill, a threshold) is judged on
that delta, one change per wave; record it in `docs/superpowers/agent-loop-plan.md`.

**Ledger line format (from the next wave).** One line per event in
`.superpowers/sdd/<plan>/progress.md`, starting with the task id so `loop-eval` parses it; free
prose may follow the fixed part. Older prose lines still parse, tolerantly.

```
Task <id>: <status> <commits>...                          status: dispatched | implemented | blocked
Task <id> review (<reviewer>): <Approved|Needs fixes>; MUST-FIX n; SHOULD-FIX n; CONSIDER n
Task <id> fix round <n>: <commits> ...; controller read the diff    (omit the last clause if re-reviewed)
Task <id> re-review (<reviewer>): <Approved|Needs fixes>; MUST-FIX n; SHOULD-FIX n; CONSIDER n
Task <id>: complete <base>..<head> ...; full suite N/0
CI <PR>: <job> <passed|failed> <reason>                   first-push result, one line per failing job
```

Rules: `<id>` is the plan's task id (`1.4`, `1.4+1.15`) or `Sweep A`; counts are numbers (`MUST-FIX 0`
when none); the `full suite N/0` figure goes on the `complete` line (tests / failures).
