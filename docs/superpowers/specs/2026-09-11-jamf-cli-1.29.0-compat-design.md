# jamf-cli 1.29.0 compatibility — design

Date: 2026-09-11. Status: APPROVED 2026-09-11 (Option A; gated names; gated `--no-verify`)
and implemented the same day on `feat/enhance-ddm`, uncommitted pending Tony's "commit".
Companion evidence: `~/Documents/Mac_Engineering/JRTroubleshooting/JR-jamf-cli-1.29.0-review-2026-09-11.md`.

## Scope

jamf-cli v1.29.0 (2026-09-11) changes three things the app depends on, verified by running
every argv the app builds against a live tenant on both binaries:

1. `pro report patch-status --scan-failures --output json` is now one JSON array of labelled
   sections instead of a `── heading ──` stream. The app's section salvage records `[]` for it,
   so patch failures read as zero on any Mac running 1.29. Data loss, effective today.
2. Three resource names the app sends are deprecated (warn on stderr until 2027-03-09, exit 2
   after): `device-enrollment-instances`, `mobile-device-inventory-details`, `ddm-status`.
   The replacements do not exist on jamf-cli ≤ 1.28 (floor is 1.18).
3. `config add-profile` verifies credentials against the server before writing unless
   `--no-verify` is passed; the flag is unknown (exit 2) on ≤ 1.28.

Out of scope: adopting `--section` for richer mobile data, the exit-8 catalog filter via the
new `api` field, `pro report software-installs --bundle-id/--path`, and every
`pro setup` change (the app never calls `pro setup`). Each is listed under Follow-ups.

Classification: bounded. Every change edits a flow that already exists (one salvage function,
three argv literals, two argument builders, docs). It ships as one themed sync, like the
1.28.0 sync (fix + chore commits).

## Change 1 — read the 1.29 patch-failure envelope

`ReportEngine.patchDeviceFailurePayload(from:onLine:)` (ReportEngine.swift, after
`jsonSections`) gains one branch ahead of the existing `device_id` scan:

- Parse each chunk as `[[String: Any]]`. If the first row carries a `section` key, the chunk
  is the 1.29 envelope. Select the element whose `section == "device_failures"`.
- If that element's `fetch_error` is a non-empty string, or `policy_failures.fetch_error` is
  non-empty (device rows depend on policy rows upstream), emit
  `[warn] patch-device-failures: upstream could not fetch <section>: <fetch_error>` and return
  nil — the caller's existing guard then records the kind as not landed. An unfetchable
  section is not a clean zero.
- Otherwise return `data` re-serialised with `JSONSerialization.data(withJSONObject:)`.
  `data` is `[]` on a tenant with no failures; that is the real answer and stays `[]`.
- The `──` path is unchanged, so 1.24–1.28 streams keep working. Neither branch depends on
  heading text or section order.

The saved snapshot stays a flat `[PatchFailureRow]`, so PatchStatusService, CoreDashboard's
"Patch Failures" sheet, HtmlReport and PatchView need no change. `policy_failures` rows have no
reader today and are not stored (YAGNI).

Tests (extend `PatchScanFailureSectionsTests`): envelope with device rows → those rows;
envelope with empty device data and empty fetch_error → `[]`; envelope with a fetch_error on
either failures section → nil plus the warn line; the three existing `──` cases unchanged.
Mutation to run: change `"device_failures"` to `"policy_failures"` in the selector and to
`""` in the fetch_error check; both must fail a test.

Docs: CLAUDE.md/AGENTS.md "jamf-cli JSON Shapes" gets the envelope as the documented
`--scan-failures` shape with the ≤1.28 stream noted as legacy.

## Change 2 — version-gated resource names

The installed version is already resolved once per collect (`detectedVersion` →
`supportsQuietFlags`, ReportEngine.swift ~1760). Add `JamfCLIInstaller.supportsSpecDerivedNames
(_ version: String?) -> Bool` = version confirmed ≥ 1.29.0, false on nil (same fail-safe
direction as `supportsQuietFlags`: never send a flag or name an older binary rejects).

- `collectCommandMatrix(profile:)` becomes `collectCommandMatrix(profile:specNames:)`.
  Two rows switch on the flag: `device-enrollment-instances list` ↔ `device-enrollments list`;
  `mobile-device-inventory-details list` ↔ `mobile-devices list`. On-disk kind names do not
  change, so `knownCollectKinds`, `CollectionTier`, readers and history are untouched.
- `ReportEngine+DeviceScan` takes the same Bool and switches `ddm-status status-items` ↔
  `declarative-device-management status-items`. This code is uncommitted 2.8.0 work with no
  snapshots in the field, so the gate lands before the feature ships.
- Below 1.29 the old names are sent exactly as today. On 1.29 the new names are sent and the
  stderr warning never appears in Run History. When the floor is later raised to 1.29, the gate
  and the old literals are deleted, not kept.

Tests: a matrix test asserting both spellings per flag for the two rows;
`DeviceScanCollectTests`' stub executable answers on both `ddm-status status-items` and
`declarative-device-management status-items`; `CollectionTierLookupTests` unchanged (kinds
are stable).

Alternatives considered: keep the old names until the floor moves (three `warning:` lines in
every collect log for six months, then a hard break with no signal in between); raise the floor
to 1.29.0 now (a floor jump of eleven minors three days before 2.8.0, on a fleet whose prod
jamf-cli version this session cannot see). Neither is recommended.

Note on the mobile pair: on 1.29 the deprecated alias resolves to exactly the call
`mobile-devices-list` already makes (`/v2/mobile-devices/detail?section=GENERAL&section=HARDWARE`),
so after this change the two kinds fetch identical 480 KB payloads. On 1.28 the "rich" call was
GENERAL-only (`hardware` null), which means the fields MobileFleetService reads from the rich
snapshot's `applications` and `userAndLocation` have been null on every version — the managed
-apps KPI has always been 0. Deduplicating the fetch and making those KPIs real are one
follow-up (below), not part of a release-week sync.

## Change 3 — `--no-verify` on `config add-profile`, version-gated

`OnboardingFlow.proOAuth2Arguments` and `platformGatewayArguments` gain a `noVerify: Bool`
parameter; the caller passes `JamfCLIInstaller.supportsSpecDerivedNames(jamfCLIVersion)`
(the same ≥ 1.29 gate — one helper, not two). When true, `--no-verify` is appended.
`ReauthenticateSheet` builds through the same functions and inherits it.

Result: the Save step keeps the semantics every doc and the 2.8.0 copy describe ("Save &
continue" writes the profile locally; the Validate step is the connection check; "Continue
without validating" still reaches a saved profile) on every supported jamf-cli. Nothing else
changes.

Alternative considered: let 1.29 verify at Save and re-run with `--no-verify` only when the
user chooses "Continue without validating". It catches a typo one screen earlier but forks the
flow by version and needs a second PTY run and copy for the failure state. Reasonable for a
later release once the floor is 1.29; not for this sync.

Tests: argument-builder tests for both gate states (pure, no PTY); the existing redaction
test is unaffected. Docs: wiki 02 "Running without jamf-cli credentials" gains one sentence
naming the flag for Terminal users on 1.29+.

The app's PTY disables ECHO on the slave (OnboardingFlow.swift:1284), so the 1.29 regression
that echoes the secret in a Terminal does not reach the GUI. No change; report upstream.

## Change 4 — tracked version and docs

- `.jamf-cli-tracked-version` → v1.29.0 (read by nothing in code; the sync routine and CLAUDE.md
  reference it). Floor stays 1.18.0; `environmentScopeVersion` stays 1.28.0.
- CHANGELOG: under [2.8.0] if the sync rides the release (Option A below), else a new
  [Unreleased] block. Plain language: "reads the new patch-failure layout", "uses the new
  command names on 1.29 and later", "saves the profile before checking it, on every jamf-cli".
- README / wiki 00, 01, 08, 10, Glossary: "tracks jamf-cli 1.28.0" → 1.29.0. Wiki 03:116 names
  `pro ddm-status status-items` → `declarative-device-management status-items`. Wiki 11 and
  docs/architecture/tiered-collection-adr.md mention `mobile-device-inventory-details` as a
  kind name (still true — the kind keeps its name).
- Wiki pages that tell a reader to run `pro setup` from a Jamf Pro account (00, 01, 02, 09)
  get a note that 1.29 defaults to `--credentials existing` and that Jamf plans to remove
  local/SAML/LDAP admin auth on cloud instances around H2 2027.

## Verified non-changes (no work)

`--from-file` (the app sends no request bodies); `pro diff` (already `--source/--target`);
`pro backup` (no `--resources`, no positional; backup + self-diff verified on 1.29);
Protect and School (0 upstream files); exit codes (usage 2, missing positional 1, both binaries;
`explainExit` map unchanged); `pro auth token --refresh` (StopGate probe) identical;
`doctor` identical; `CapabilityService.trackedCommands` all present in 1.29 `pro --help`;
the 2.6.2 `stdoutFallbackFile` for `pro device` now no-ops on 1.29 (measured: the CLI writes the
`--out-file` and leaves stdout empty; the fallback writes only when stdout is non-empty) and stays
for ≤ 1.28; the #365 scope-withholding rule needs `JAMF_CLIENT_ID` in the child environment, which
`CLIBridge.environmentForJamfCLI` never passes through (fixed keys plus the six proxy variables only); `pro report ddm-status` (the
report) is untouched — only the generated `pro ddm-status` resource is deprecated.

## Release placement — Tony's call

- **Option A (recommended): ride 2.8.0.** Two commits on `feat/enhance-ddm` after the themed
  split in HANDOFF.md: `fix(collect): read the 1.29 patch-failure envelope` (Change 1) and
  `chore(jamf-cli): sync to v1.29.0` (Changes 2–4). Roughly 60 lines plus tests. Gate: build,

  Monday date; accepts the two regressions above for anyone who upgrades jamf-cli first.

## Follow-ups (not in this sync)

  --section GENERAL --section HARDWARE --section SECURITY --section APPLICATIONS

  verify-at-Save onboarding flow.
